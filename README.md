# wb-search-top

Сервис реального времени «Сейчас ищут» — отдаёт топ самых популярных поисковых запросов за последние 5 минут.

---

## Быстрый старт

**Требования:** Docker, Docker Compose, Go 1.25+

```bash
# Поднять сервис + Kafka одной командой
make up

# Сервис будет доступен на http://localhost:8080
# Kafka — на localhost:9094 (для локальной разработки вне Docker)
```

## API

Base URL: `http://localhost:8080`

### GET /top

Возвращает топ поисковых запросов за последние 5 минут.

**Query params:**

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `n` | int | Нет | Количество позиций (1–100). По умолчанию — `max_top_limit` из конфига |

**Пример запроса:**
```bash
curl "http://localhost:8080/top?n=10"
```

**Пример ответа:**
```json
{
  "items": [
    {"query": "кроссовки найк", "count": 42},
    {"query": "платье летнее",  "count": 31},
    {"query": "джинсы",         "count": 17}
  ],
  "total": 3
}
```

**Коды ответа:**

| Код | Описание |
|-----|----------|
| 200 | Успех |
| 400 | Невалидный параметр `n` |
| 429 | Превышен rate limit (100 req/s с одного IP) |

Добавляет слово в стоп-лист. Слово мгновенно исчезает из топа, в том числе для уже накопленных данных.

**Body:**
```json
{"word": "спам"}
```

**Пример:**
```bash
curl -X POST http://localhost:8080/stoplist \
  -H "Content-Type: application/json" \
  -d '{"word":"нежелательный запрос"}'
```

## Контракт данных (Kafka)

**Топик:** `search-logs`  
**Формат:** JSON, UTF-8  
**Партиции:** 3

### Структура сообщения

```json
{
  "query":     "кроссовки найк",
  "user_id":   "u-8f3a1c9b",
  "timestamp": "2025-05-25T12:34:56.789Z"
}
```

### Обоснование полей

| Поле | Тип | Обязательное | Зачем нужно |
|------|-----|--------------|-------------|
| `query` | string | Да | Сам поисковый запрос — основа всей логики |
| `user_id` | string | Да | Дедупликация: один пользователь = 1 голос за бакет. Без этого поля сервис не может отличить 1000 запросов одного бота от 1000 уникальных пользователей |
| `timestamp` | RFC3339 | Да | Корректная обработка запоздавших сообщений из Kafka. Без него запоздавшее сообщение попадёт в текущий бакет вместо исторического |

### Обработка невалидных сообщений

- Битый JSON → сообщение логируется и пропускается, offset коммитится
- Пустой `query` → тихий пропуск, не считается ошибкой
- Пустой `user_id` → fallback: `"anon-" + timestamp`, функциональность сохраняется, защита от накрутки ослаблена

Проект построен по **гексагональной архитектуре** (ports & adapters): `core/` не знает ни о Kafka, ни о HTTP. Зависимости направлены внутрь — к интерфейсам `core/ports.go`.

### Хранилище топа — скользящее окно

Ключевая структура — **кольцевой буфер бакетов**:

```
Окно 5 минут = 30 бакетов × 10 секунд

[t-29][t-28]...[t-1][current]
  ↑                     ↑
удаляется          сюда пишем
каждые 10s
```

Каждый бакет хранит `map[query]map[userID]struct{}` — множество уникальных пользователей для каждого запроса. Это даёт **автоматическую дедупликацию**: бот, отправивший один запрос 10 000 раз, занимает ровно одну ячейку в бакете.

**`GetTop`** мержит множества userID по всем бакетам — пользователь, попавший в несколько бакетов, считается ровно один раз.

**Сложность операций:**

| Операция | Сложность |
|----------|-----------|
| `Increment` | O(1) |
| `GetTop(n)` | O(U) где U — уникальных (query, userID) пар в окне |
| `rotate` (каждые 10с) | O(B) где B — размер старого бакета |

### Стоп-лист

`map[string]struct{}` под `sync.RWMutex`.

- `Contains` — только `RLock`, тысячи параллельных читателей не блокируют друг друга
- `Add`/`Remove` — `Lock`, вызываются редко (ручное управление)

Фильтрация стоп-слов работает **в двух местах**:
1. **При записи** (`ProcessEvent`) — новые события не попадают в бакеты
2. **При чтении** (`GetTop`) — старые события мгновенно пропадают из топа после добавления слова в стоп-лист

## Trade-offs и бизнес-логика

### Выявленные неточности в постановке и решения

**1. «Топ за последние 5 минут» — что значит «последние»?**

Скользящее окно vs фиксированное (например, 12:00–12:05, 12:05–12:10). Выбрано **скользящее окно** — оно всегда актуально, не сбрасывается раз в 5 минут и даёт плавный результат для виджета.

**2. Что считать — клики или уникальных пользователей?**

Выбраны **уникальные пользователи за окно** (не клики). Обоснование: «популярный запрос» — тот который интересен многим людям, а не тот который один человек повторил тысячу раз. Это и является встроенной защитой от накрутки.

**3. Гранулярность бакета**

Выбрано 10 секунд — компромисс между точностью и памятью. При 10s бакете данные устаревают максимум на 10 секунд. Уменьшение до 1s увеличит точность, но в 10 раз больше map-аллокаций.

**4. Накрутки конкурентов**

Решено на уровне структуры данных: `map[userID]struct{}` в каждом бакете. Дополнительно стоп-лист позволяет оперативно убрать аномальный запрос.

**5. Запросы читаются в 10–50 раз чаще чем пишутся**

`GET /top` использует `RLock` — все читатели работают параллельно без блокировок. Запись (`Increment`) берёт `Lock` только на время добавления в текущий бакет — O(1).

### Компромиссы ради производительности

- **Память vs точность:** бакеты хранятся полностью в памяти. При очень большом числе уникальных запросов и пользователей потребление памяти может вырасти. Для продакшена стоит добавить лимит на размер бакета.
- **At-least-once vs exactly-once:** событие может обработаться дважды при рестарте сервиса между обработкой и коммитом. Для статистики топа это допустимо — один лишний голос не критичен.
- **Timestamp игнорируется при записи в бакет:** запоздавшее из Kafka сообщение попадёт в текущий бакет, а не в исторический. Альтернатива — искать нужный бакет по timestamp, но это усложняет `rotate()` и требует дополнительной синхронизации. Для 5-минутного окна запаздывание редко превышает секунды.

## Мониторинг

Сервис экспортирует метрики в формате Prometheus на `GET /metrics`.

**Основные метрики:**

| Метрика | Тип | Описание |
|---------|-----|----------|
| `http_requests_total` | Counter | Кол-во запросов по методу, пути, статусу |
| `http_request_duration_seconds` | Histogram | Время ответа (buckets: 1ms–1s) |
| `kafka_events_processed_total` | Counter | Обработанные события по статусу (ok/error) |
